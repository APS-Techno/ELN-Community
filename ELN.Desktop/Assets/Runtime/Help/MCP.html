Local MCP integration

The Community MCP host exposes local notebook tools over standard input and output. It does not provide a remote server, login API, team administration or an AI/RAG subsystem. A client that launches it can read or change records within the local principal's permitted scope.

Prepare a local session

  1. Create a Community notebook in the desktop. Close the desktop before using the same notebook in an MCP session.
  2. Select the database and its matching attachment directory. Create a separate upload directory and a plugin directory. Both directories must exist; an empty plugin directory is valid if no viewer extraction is needed.
  3. Place only intended upload inputs under the upload root. Use local directories without junctions or symbolic-link aliases.
  4. Configure your MCP client to launch the host with four absolute paths:
ELNCommunityMCP.exe --notebook "C:\ELNExample\notebook.sqlite" --storage "C:\ELNExample\attachments" --upload-root "C:\ELNExample\uploads" --plugins "C:\ELNExample\plugins"

The paths are examples, not supplied directories. The host only opens an existing notebook; it does not create one or migrate it. Each option also accepts --name=value. Do not use the Desktop-only --config option here.

Transport and tool discovery

The transport reads one UTF-8 JSON-RPC request per line and writes one response per request with an ID. Notifications have no response. Diagnostic messages go to standard error; they are not JSON-RPC response lines. Closing standard input ends the session normally. Use a client compatible with this line-based stdio transport.

{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"list_projects","arguments":{}}}

Read the current tools/list schemas instead of guessing arguments. The selected host currently registers 62 tools. Scientific tools include create_project, create_item, add_value, add_values and get_values, together with navigation, search, files and Wiki functions. Read-only author metadata is not account administration.

Values and their sources

Store each measured or calculated number as a value with a source, not only as item text. The source tells where the number came from.

  • Reader: the number came from a viewer reader. Call extract_file_key_values first. Its result gives file_id, reader_id and reader_version. Pass these to add_value as source_file_id, reader_id and reader_version, and pass the key value name as key_name.
  • Manual: the number came from an analysis or was typed. Pass source_file_id (the analysed file), source_note (for example job or run IDs), or both.
  • Unknown: a call without source fields stores the value with source kind Unknown. Values stored before sources existed also show Unknown.

The source file must belong to the item, one of its ancestors or one of its descendants in the same project. A file from another project or from an unrelated item is refused. get_values, get_item and query_values return the source of each value. add_values stores up to 200 values in one step. It checks all entries first; if one entry is refused, the error names its index and no value is stored.

A value outside the plausible range of its value type is refused. A tolerance larger than the value magnitude, or smaller than the value magnitude divided by the tolerance factor (default 1000), is also refused. list_value_types shows range_min, range_max and tolerance_factor. Check the number and its units first. Only if the value is correct, repeat the call with confirm_out_of_range: true; the response then lists the confirmed issues.

Read-only checks

  • check_value_drift runs the current reader again on the source file of each Reader value of an item or project. It lists only the values whose number, reader or reader version changed, or whose file or key is missing.
  • report_value_issues lists stored values outside their type range or with an inconsistent tolerance. It changes nothing.
  • check_storage compares the bytes in attachment storage with the hash recorded at upload. It reports each file as ok, missing, content_mismatch, no_hash or error. Give a baseline list of files from an earlier report to see their current status in previously_reported. It never repairs a file; use repair_files for missing bytes.

Write and review boundaries

  • Created records belong to the current local principal. A supplied owner parameter cannot turn a local session into another user's session.
  • Writes to signed items and foreign or missing projects/items are refused. The tool manager reloads the active principal before each tool call.
  • upload_file reads only an allowed source path under the upload root. A path outside that root is refused; do not broaden the root to an entire disk.
  • Human hypothesis approval and conclusion acceptance are not MCP tools. Calling approve_hypothesis or accept_conclusion returns tool-not-found. Perform those gates in the desktop.

An automation client can make persistent changes. Check its requested tool and arguments before permitting writes, keep backups, and use a synthetic notebook for integration tests. Local signatures and review states are not substitutes for operating-system access controls.
