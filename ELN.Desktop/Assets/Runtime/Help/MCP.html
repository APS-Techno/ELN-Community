Local MCP integration

The Community MCP host exposes local notebook tools over standard input and output. It does not provide a remote server, login API, team administration or an AI/RAG subsystem. A client that launches it can read or change records within the local principal's permitted scope.

Prepare a local session

  1. Create a Community notebook in the desktop. Close the desktop before using the same notebook in an MCP session.
  2. Select the database. Create a separate upload directory and a plugin directory. Both directories must exist; an empty plugin directory is valid if no viewer extraction is needed.
  3. Place only intended upload inputs under the upload root. Use local directories without junctions or symbolic-link aliases.
  4. Configure your MCP client to launch the host with absolute paths:
ELNCommunityMCP.exe --notebook "C:\ELNExample\notebook.sqlite" --upload-root "C:\ELNExample\uploads" --plugins "C:\ELNExample\plugins"

The paths are examples, not supplied directories. The host uses the attachment directory saved in the notebook. For a notebook without a saved directory, add --storage "C:\ELNExample\attachments"; an explicit --storage also overrides the saved directory. The host never saves a directory in the notebook. The host only opens an existing notebook; it does not create one or migrate it. Each option also accepts --name=value. Do not use the Desktop-only --config option here.

The Windows installer installs ELNCommunityMCP.exe in the program folder, beside ELNCommunity.exe. The default folder is %LocalAppData%\Programs\ELN Community. Use the full path of this file in your MCP client.

Transport and tool discovery

The transport reads one UTF-8 JSON-RPC request per line and writes one response per request with an ID. Notifications have no response. Diagnostic messages go to standard error; they are not JSON-RPC response lines. Closing standard input ends the session normally. Use a client compatible with this line-based stdio transport.

{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"list_projects","arguments":{}}}

Read the current tools/list schemas instead of guessing arguments. The selected host currently registers 69 tools. Scientific tools include create_project, create_item, add_value, add_values, add_derived_value, update_value, remove_value, remove_values, delete_file and get_values, together with navigation, search, files and Wiki functions. Read-only author metadata is not account administration.

Search by meaning

search_semantic finds records by meaning. It takes query, an optional top_k (1 to 50, default 10) and an optional project_id. Before it searches, it updates the index. Reading files can take up to 20 seconds. If that time is not enough, indexing can take up to 20 more seconds. The result has an index object with complete, indexed_passages, pending_passages and files_pending (files that are not read yet). If complete is false, call the tool again to finish the update. The index includes the text of PDF, Office, HTML, JSON, XML, CSV, RTF, Markdown and text attachments. The result also has groups, one group for each item, best first. top_k counts groups. Each group has item_id, item_title, project_id, project_path, score, sources and up to 3 passages. Each passage has field, file_id, snippet and score.

Filters of search by meaning

search_semantic takes these optional filter parameters: folder_id (the folder and its subfolders), item_types (an array of item types, for example Measurement), levels (an array of Proc, Item, Action or Folder), action_type_id, date_field (created, the default, or modified), date_from and date_to (ISO 8601 dates, for example 2026-01-31) and values. The tool includes the whole first day and the whole last day. An item without a modified date does not match a modified filter. Each entry of values has value_type (title or symbol), min and max (both limits are inclusive), unit and rec_type (EXP_CONDITION or TEST_RESULT). An item must match every entry. The tool converts min and max from unit into the unit of the value type. For example, 10 GPa is 10000 for a value type in MPa. If unit is empty, the limits are already in the unit of the value type. A unit of another dimension, for example mm for a hardness, is an error. It is not an empty result.

The tool applies the filters before the ranking, so a strict filter finds matching items that a plain search would rank low. A filter never gives access to more projects. A folder that you cannot read returns the same error as a folder that does not exist. The parameters are explicit. The tool does not read a filter from the query text. When you use a filter, the result has filters_applied. It shows the filter that the tool used, with the min and max limits converted into the unit of each value type and the unit you requested in requested_unit. A wrong parameter, an unknown unit or an unknown value type returns an error with the reason.

The score is a rank-fusion value. Use it only for the order of the results. It is not a probability and it is not a relevance percentage. Do not compare it with a fixed limit. When reranked is true, the groups are not in the order of their score values.

The result has the field reranked. It is true when the optional reranking model sorted the groups. The model reads the query and the best passage of each group, with the location of the item (project, folders, item title and type). It sorts the first 20 groups. The groups after the 20th keep the order of the normal search. reranked is false when the model is not installed, when it needs more than 1.5 seconds, when it fails, or when the result has only one group. In these cases the groups are in the order of the normal search, and the tool works as before. The first call after the MCP server starts can take more time, because the server loads the model.

The tool needs the downloaded model files. Install them in the Desktop with Tools > Semantic Search Setup.... If they are not there, the tool returns an error that says semantic search is not installed. If the model cannot start, the error says could not start: <cause> [semantic_search_unavailable]. The search tool does not need these files. The MCP server and the Desktop can share one index file; each loads its own model copy.

Find a file and read tabular data

File matches from search include file_id, full_name and extension. Use the returned file ID for file tools; do not infer it from the display title. The full filename keeps compound extensions such as .depo.json and .process.log. Extraction responses also identify the file, so keep that identity with its results.

  1. Call list_file_columns with file_id to inspect column indices, names, units, types and the available row count.
  2. Call get_file_columns with file_id and columns. Select columns by index or by an unambiguous name.
  3. Use mode: "stats" for summary numbers, "downsample" for a min/max-binned series, or "raw" for unbinned rows. Downsample is the default. Its max_rows parameter defaults to 500; min/max bins can return up to twice that number of points. Use an optional half-open row_range: [start, end] for raw or downsample reads.

Columnar access requires a loaded viewer that supports it. A supported file extension alone does not guarantee a valid table. Start with statistics or a downsampled view before requesting a large raw series.

Values and their sources

Store each measured or calculated number as a value with a source, not only as item text. The source tells where the number came from.

  • Reader: call extract_file_key_values first. Raw key values remain in value and units. For a mapped key, store converted_value with its value_type_id and mapped_description. Pass source_file_id = file_id, reader_id, reader_version, key_name = name, reader_units, and conversion_factor. If the key has an analysis_snapshot (for example ZRW COF), pass it unchanged too; without it the value cannot be re-checked over its interval. When a key was left out, analysis_status gives the reason: no_plateau, stale_selection, interval_unusable or no_step_found (a .fibps scan with neither a step nor a wear groove). low_confidence means that a Step Height was returned but is weak; check the regions before you store it. Unmapped keys give unmapped_reason; do not guess a conversion.
  • Manual: the number came from an analysis or was typed. Pass the analysed source_file_id, a source_note, or both.
  • Unknown: a call without source fields stores Unknown. Values stored before sources existed also show Unknown.

extract_file_key_values pairs matching STD keys within that extraction and omits separate STD entries. A mapped main value includes tolerance in its target unit when STD is valid, including zero. Pass this field to add_value or add_values. Invalid STD is reported in tolerance_warning; orphan STD is reported in the top-level warnings array. Missing or invalid STD has no tolerance field. Drift checks do not compare tolerances.

extract_file_key_values accepts an optional selection (JSON object) for this call only; it is never stored. A reader without analysis support, or a selection the reader cannot use (interval_unusable, stale_selection), is refused with an error. For a .fibps file the selection is {"rect_a":[x0,y0,x1,y1],"rect_b":[x0,y0,x1,y1],"pix_w":W,"pix_h":H}: inclusive pixel indices of the two flat regions; pix_w and pix_h must equal the map size. The result then has Step Height from those rectangles and an analysis_snapshot with mode regions; pass it unchanged to add_value or add_values. To choose the rectangles, call extract_file_data on the .fibps file: data.heightMap is the levelled height map downsampled to at most 96 cells per side, with x_px and y_px (first-pixel index of each cell) and stride.

The source file must belong to the item, one of its ancestors or one of its descendants in the same project. A file from another project or from an unrelated item is refused. get_values, get_item and query_values return the source of each value. add_values stores up to 200 values in one step. It checks all entries first; if one entry is refused, the error names its index and no value is stored.

A value outside the plausible range of its value type is refused. A tolerance larger than the value magnitude, or smaller than the value magnitude divided by the tolerance factor (default 1000), is also refused. list_value_types shows range_min, range_max and tolerance_factor. Check the number and its units first. Only if the value is correct, repeat the call with confirm_out_of_range: true; the response then lists the confirmed issues.

A number calculated from other stored values by a named formula is a Derived value. Store it with add_derived_value, not with add_value: give item_id, formula_id, inputs (role → value ID) and optionally description and confirm_out_of_range. The server calculates the number; a call that also sends value or any other field is refused. Formula wear_rate_reciprocating (version 1) calculates K = A / (2 · F · N) in mm³/(N·mm) from the roles area (Wear area, mm², zero allowed), normal_force (Normal force, N) and cycles (Cycles, no unit). Every input must have the required type and unit and be stored on the item or an item below it in the same project. An input can be a Derived value; a dependency cycle is refused. No tolerance is stored. The source in get_values, get_item and query_values shows formula_id, formula_version and the inputs with the numbers used. A notebook without Derived storage refuses the call.

The area role of wear_rate_reciprocating also takes an array of Wear area value IDs, for example "inputs":{"area":[12,15,16],"normal_force":13,"cycles":14}. The server uses the mean of the areas and stores every ID as an input. An array for a role that takes one value, or the same ID twice, is refused.

A Derived result is stored. Editing or deleting an input does not update or delete it. Run check_value_drift to find changed or missing dependencies. Use add_derived_value again for a new result when the inputs change.

update_value changes a stored value in place. Give value_id and one or more of value, tolerance, description, rec_type and value_type_id. For a Reader value you can also give reader_version and analysis_snapshot, for example after a reader fix. An empty analysis_snapshot deletes the stored snapshot. The source kind and the other source fields do not change; for another source, remove the value and add a new one. The number of a Derived value cannot be changed. A new number, tolerance or value type goes through the same range checks as add_value. The response shows the old fields in previous, and changed: false when nothing was different.

remove_value deletes one value; remove_values deletes up to 200 values, all or nothing. An optional reason goes into the audit. The analysis snapshot of the value is deleted with it. A Derived value that used the removed value as an input stays; the response lists it in dependent_derived_value_ids.

You cannot undo these changes from MCP. The audit log keeps the old number, tolerance, value type and description: for a change in the value row (get_audit_log with entity_type Value), for a removal in a row of its item (entity_type Item). Both tools refuse a value of a signed or deleted item, and a value whose item is a run of, or is cited by, a hypothesis in review or accepted.

delete_file deletes a file permanently. It also deletes the Reader values that came from the file and their analysis snapshots; Manual and Unknown values stay. dry_run is true by default: call it first and read values_to_delete. Give confirm_hash (the hash from list_files) to protect against a changed file. The tool needs write access. It refuses a file of a signed or deleted item, and a file or item that is a run of, or is cited by, a hypothesis in review or accepted. The record and its values are removed in one database transaction; if it fails, nothing is removed. bytes_status is removed, absent or remaining; the file record is deleted even when the bytes remain. list_files and get_item show is_deleted for a file whose item or an ancestor is in the Recycle Bin. list_files with check_storage adds storage_status.

Read-only checks

  • check_value_drift runs the current reader again on the source file of each Reader value of an item or project. It lists only the values whose number, reader or reader version changed, or whose file or key is missing. It also calculates each Derived value again from its inputs (Reader inputs read again, Derived inputs calculated again, Manual inputs as stored) with the saved formula version, and reports value_changed, input_changed, input_missing, formula_version_changed, formula_version_mismatch, dependency_cycle, read_failed or not_fully_rerunnable (a Manual or Unknown value is in the input tree). A Derived row has source_kind Derived, the formula versions and an inputs list.
  • report_value_issues lists stored values outside their type range or with an inconsistent tolerance. It changes nothing.
  • check_storage compares the bytes in attachment storage with the hash recorded at upload. It reports each file as ok, missing, content_mismatch, no_hash or error. Give a baseline list of files from an earlier report to see their current status in previously_reported. It never repairs a file; use repair_files for missing bytes.
  • download_file copies the stored bytes of one file to dest_path, which must be under the upload root of the MCP server. It returns the size, the MD5 and storage_status (ok, content_mismatch or no_hash). If the bytes are missing, it writes nothing. It does not replace an existing file unless overwrite is true.

Reader drift checks use the saved factor, not the current mapping. A changed emitted unit is reported as reader_units_changed without applying the old factor. Legacy Reader values without conversion metadata retain their raw-output comparison.

A Reader value saved with an analysis snapshot is calculated again over the stored interval or regions, also when the file hash changed. The check reports source_changed (file differs from the snapshot), selection_changed and interval_unusable (the stored interval or regions cannot be used for the current file; no number is compared) separately from value_changed. For an interval snapshot (ZRW), selection_changed means the shared interval differs from the snapshot; a missing shared interval counts only for a manual snapshot. For a regions snapshot (FIBPS), the stored regions are replayed; selection_changed is reported only when the snapshot names the shared selection it came from (shared_revision, shared_apply_id) and that selection is missing or has changed.

Write and review boundaries

  • Created records belong to the current local principal. A supplied owner parameter cannot turn a local session into another user's session.
  • Writes to signed items and foreign or missing projects/items are refused. The tool manager reloads the active principal before each tool call.
  • upload_file reads only an allowed source path under the upload root. A path outside that root is refused; do not broaden the root to an entire disk.
  • Human hypothesis approval and conclusion acceptance are not MCP tools. Calling approve_hypothesis or accept_conclusion returns tool-not-found. Perform those gates in the desktop.

An automation client can make persistent changes. Check its requested tool and arguments before permitting writes, keep backups, and use a synthetic notebook for integration tests. Local signatures and review states are not substitutes for operating-system access controls.
