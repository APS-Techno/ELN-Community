Notebooks, identity and backup

Keep the database and attachments together

A complete notebook consists of its .sqlite database and its matching attachment directory. Keep the directory structure and filenames unchanged. Attachment metadata alone cannot restore missing file bytes.

The signing password is not a database-opening password. Protect the database, attachment directory, backups and retained drafts with operating-system access controls. Community is not an encrypted notebook or a multi-user server.

Open or switch a notebook

  1. Choose File → Open Notebook... and select the Community database.
  2. Select that notebook's attachment directory, not a directory from another notebook.
  3. If another notebook is active, finish or cancel its pending editor and working-draft decisions. The candidate is validated before the active notebook is released.
  4. Check the notebook path and local identity in the main window before making changes.

Opening does not create a database or migrate an existing database. The supported local format is version 2 and requires exactly one active identity. Commercial databases, unsupported local formats and SQLite WAL-mode databases need a separately controlled conversion; changing a marker or deleting a user record is not a conversion.

Choose File → Close Notebook before reopening the same database with a different attachment root. Preferences cannot relocate storage. When moving a closed notebook, move the database and its matching attachment directory as a pair, then select their new locations.

Notebook records are stored in the database as you complete their edit commands. There is no separate Save Notebook step. Normal shutdown does not show a temporary-directory retention notice.

Local identity and signing

Notebook creation records the name supplied in the local-profile dialog and creates one ordinary local identity. No Admin promotion or team account is needed. The current Community desktop has no separate profile-edit command. Use the original signing password for record signing; opening a notebook does not request it.

Make a consistent backup

  1. Save intended changes. Resolve editor conflicts and note any retained draft or recovery directory.
  2. Close the notebook and stop all Desktop and MCP processes that use it. Do not copy a database while a writer is active.
  3. Copy the database and the entire attachment directory into one backup set. Keep their association clear.
  4. Copy any retained working-draft/recovery directory separately if it contains changes you still need. A draft is not part of the saved attachment tree.
  5. Restore into a new location, not over an open notebook. Open the restored database with the restored attachment directory and check representative records and attachments before relying on it.

Do not delete -journal, -wal or -shm files to make Open succeed. Close or recover the database in its owning client first. Preserve the database, sidecars and attachments if recovery is needed.

Scientific package export and PDF export are not full notebook backups. The current package importer restores only its supported metadata/protocol subset, not a complete record/file/value hierarchy. See reports and packages.

Launch with explicit paths

ELNCommunity.exe --config "C:\ELNExample\desktop.ini" --notebook "C:\ELNExample\notebook.sqlite" --storage "C:\ELNExample\attachments" --plugins "C:\ELNExample\plugins"

These are illustrative paths; create or select your own existing notebook and runtime plugin directory. Supply --notebook and --storage together. --config selects the local settings file. Explicit notebook paths take priority over the saved location. Without these arguments, Community reopens the last successfully opened notebook with its matching attachment directory. On first use, choose New Notebook or Open Notebook. If a saved location is unavailable, Community explains the problem and leaves the welcome screen usable; it does not create a replacement notebook.
